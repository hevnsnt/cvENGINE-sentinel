# Changelog

## Unreleased

### Added
- **Web service features: HTTP/3, PHP on Windows, WebDAV and the methods a server lists, the VPN portals of five appliances, and SLP (`probes.service_reads`).** So cvENGINE can rule out, or support, a CVE that needs one of them on. Ten features join the vocabulary (`http3`, `php_windows`, `webdav`, `http_methods`, `vpn_fortinet`, `vpn_globalprotect`, `vpn_cisco`, `vpn_citrix`, `vpn_ivanti`, `slp`). The `http_probe` batch reads `http3` (`Alt-Svc` advertises `h3` or `h3-NN`; `no` only means not advertised: a QUIC listener nobody advertises is not read, and no QUIC packet is sent) and `php_windows` (PHP named with IIS, Win32 or Win64, or with a Unix or distribution token; CGI mode and the code page are not readable from outside) from the front page answer `headers-root` already fetches: no request of its own. An entry's new optional `features` list asks for reads that cost a request, once per web base: `webdav` sends one `OPTIONS /` (`probes.http.probe_url` now allows OPTIONS beside GET and HEAD) and believes WebDAV only from a `DAV` compliance class or `MS-Author-Via: DAV`, never from an `Allow` list alone, and not at all when the answer is the front page again (`soft404.same`: a server that answers every method alike); `http_methods` says which of PUT, DELETE, TRACE and PROPFIND `Allow` and `Public` list. `vpn_*` GETs the vendor's own portal pages (FortiGate `/remote/login`; GlobalProtect `/global-protect/login.esp` then the gateway's `/ssl-vpn/prelogin.esp`, never `hipreport.esp`; Cisco `/+CSCOE+/logon.html`; NetScaler `/vpn/index.html` then `/logon/LogonPoint/index.html`; Ivanti `/dana-na/auth/url_default/welcome.cgi`): a page with the vendor's markers that a path which cannot exist beside it does not also get is `yes`, a 404 on every path `no`, and a login page every path gets is unknown, never "present". The `hygiene_check` target's new optional `slp` list gets one SLPv2 Service Request for `service:VMwareInfrastructure` over TCP 427 per endpoint (`yes`: an SLP reply; `no`: the connection was refused, direct connections only; UDP is not read and nothing is ever registered, so the CVE-2023-29552 amplification is not touched). Every reading goes out as a `service_features` item; a read that was not taken is no item. The target fields are optional and additive (an older Sentinel ignores them and reads nothing), so the contract version is unchanged.
- **Service features: one shared vocabulary for what a Sentinel reads about a feature of a service (`cvengine_scanner.features`).** Some flaws are reachable only with a feature on (HTTP/2, an SSH algorithm, SMB compression). `features.FEATURES` is the closed vocabulary (`{key: {'values', 'transport', 'about'}}`, keys `[a-z0-9_]{1,32}`), and `features.clean_features(items)` the validator both sides apply: an item is `{host, port, transport, feature, value, detail?}`, its value one allowed token or several joined by commas (64 characters at most), `detail` plain text (200 at most), `port` 1 to 65535, `transport` `tcp` or `udp` and the feature's own, at most 128 items; anything malformed or unknown is dropped, never repaired, and an item not taken is unknown, never "no". Any result kind may carry such a list as the optional `service_features` field (`$defs/service_features` in the contract, allowed on every result), so no contract bump. The first feature is `http2` (`yes` / `no`, the ALPN answer in `detail`), which the `hygiene_check` batch now reports for every handshake whose ALPN answer it read.
- **The TLS hygiene probe says whether each service offers HTTP/2 (`alpn` on a `hygiene_check` certificate).** The handshake that already reads the certificate now offers ALPN `h2` and `http/1.1`, and the certificate row carries what the server chose: `h2`, `http/1.1`, `none` (it chose nothing, so no client reaches HTTP/2 over TLS there) or `unknown` (not read). No extra connection, and the certificate, protocol, cipher, chain and legacy-TLS readings are the same as without the offer (a test against a local TLS server compares both). A server that aborts the handshake on the offer (RFC 7301's `no_application_protocol` alert) is read again without it and reports `unknown`; the legacy TLS 1.0 / 1.1 client offers no ALPN and reports `unknown`. Cleartext HTTP/2 (h2c with prior knowledge) is not probed: nginx and most servers need explicit configuration for it, so a plain-HTTP port stays unknown. cvENGINE uses the reading to rule out or support CVEs that need HTTP/2 (the nginx HTTP/2 module flaws). The batch reports it as a service feature (below). The fields are optional, so the contract version is unchanged and an older server ignores them. `probes.tls` (the `supplier_check` copy, for a supplier's domain rather than a host) is unchanged.
- **The heartbeat says what this machine has and how it is doing (`info.machine`), so cvENGINE can tune each Sentinel's concurrency from its own numbers.** `cpus` and `host_cpus`, the load average, memory and swap (`/proc/meminfo`), the container's memory limit, use and out-of-memory kill count (cgroup v2, else v1), and `oom_kills_1h`: runs of each task kind the kernel killed for memory in the last hour (`client/machine.py`; the daemon counts a task that ends with `ToolOOMError` or a bbot run that was killed). Numbers only. The field is optional, so the contract version is unchanged and an older server ignores it.
- **Contract 11: the template index, so the cvENGINE server keeps no copy of the nuclei templates and resolves no target name.** All scanning runs on the Sentinels, so the server no longer builds nuclei, downloads the template library or packs an approved bundle. The library ships `cvengine_scanner/data/nuclei_template_index.json`: for every template of the pinned release (v10.5.2, 14,225 files) its path, sha256, id, tags, metadata vendor and product, CPE and the verdicts of this library's rules (`refuse`: over 200,000 bytes or not UTF-8; `ro`: `checks.readonly_problem(text, allow_credentials=True)`; `cred`: `checks.credential_problem`; `ctag`: tagged default-login or bruteforce). `cvengine_scanner.template_index` reads it (`policy_problem` composes the verdicts as the server's rule for an installed template does, measured equal on every file of v10.5.2; `approved`, `for_cve`, `by_sha256`), and `scripts/generate_template_index.py` makes it, cross-checked with the service-port allowlist; `scripts/check_tool_versions.py --fail-if-behind` fails when the pinned release moves and the index is not made again. `checks.readonly_problem` takes `allow_credentials`. A nuclei target's `template_policy` may say `source: "index"` (and no longer needs `bundle_sha256`): the Sentinel builds the approved set from its baked templates and the index (`client.templates.ensure_index_set`: a file runs only when the index records its path with exactly its sha256 and the verdict passes the policy; a missing or changed file is left out, and nothing approved in the image is an error), and names it `index:<release>:<policy>` in `templates_release`. A `nuclei_validate` test may name an installed template by `template_path` instead of sending its text (`client.templates.installed_text`), and its result then carries the text it ran (`template`), so the server can read what a hit showed without keeping a copy of its own. A nuclei target scope refuses (a name that now resolves to an address no Sentinel may scan) is named in `not_checked` with a reason that starts `refused by scope: ` (`flags.NUCLEI_REFUSED_PREFIX`) and in `unreachable`, and the task's other targets still run, instead of the whole task failing: the server no longer looks the names up before it sends them. A nuclei target may carry `external: true` (every task the server does not send as internal work): each target, and every address a name resolves to, is then judged as a Sentinel that is not internal judges it, whatever this machine's setting, so a name of an outside target that now points into a private network is refused here as the server used to refuse it. `flags.TEMPLATE_INDEX_SINCE` (11) is the contract a Sentinel must declare before the server sends it such work; an older server's bundle is still fetched and run as before. The version 10 results are frozen under `fixtures/results/v10/`.
- **An unidentified service's fingerprint is sent whole enough to read, and the version scan's own scripts are sent apart.** nmap's service fingerprint (`servicefp`, the escaped raw replies of a service it could not name) was cut at 1,024 characters, inside the first reply's headers; it is now kept to 4,096 (the banner script's text stays at 1,024), and cvENGINE decodes it for the greeting and the HTTP headers. The output of the scripts a version scan runs on its own (nmap's `version` category: `vmware-version`, `rpcinfo` ...; still never stored among the reviewed scripts) is sent as a port's `version_scripts` (at most 8 scripts, 2,000 characters each, 8,000 a port; cuts named `version_scripts` and `version_script_output`). No new request: both are what nmap already printed. The contract gains the optional field and the longer banner bound; a server that predates them clips the banner and drops the field, so the contract version is unchanged.
- **Contract 10: the network detection pass, so cvENGINE can name and version the services that do not speak HTTP.** The light pass runs `-tags tech`, which only the http technology templates carry: a host's RDP, Redis, MongoDB, MySQL, VNC, RabbitMQ, ActiveMQ, SSH and FTP ports got nothing from it (no network template is tagged `tech`; the `network/detection/` templates are tagged `network,detect` plus their product). A `nuclei_light` target may now carry `network_detection: true`: its non-web `host:port` targets each run the templates of their class that are on the service-port allowlist and whose reviewed path (the allowlist's `path`, never where a bundle puts the file) is under `network/detection/` (`flags.nuclei_detection_selection`, `flags.is_detection_path`, `nuclei_allowlist.is_detection` and `detection_classes`): nuclei's raw tcp type only, one template at a time under the service budget, `dos`, `default-login`, `bruteforce`, `fuzz` and `intrusive` always excluded, and the content rule as for every service run. Never `network/cves`, a misconfiguration, an exposure, a c2 or honeypot check, a javascript or ssl template, an http template or the task's tags. A web target in such a task is not run (named in `not_checked`); a class with no detection template (`tls`, `smb`, `mssql`, `postgres`, `ldap`, `memcached`) answers "no check exists for this service". The result is a `nuclei_light` result as before. `flags.NUCLEI_DETECTION_BUDGET` (240 s a port) and `NUCLEI_DETECTION_MAX_PORTS` (3 a task) keep a task inside the light pass's 840 s; `NUCLEI_DETECTION_SINCE` (10) is the contract a Sentinel must declare before the server sends it the field (an older one would ignore it and check nothing). `fixtures/nuclei/network_detection.jsonl` holds realistic result lines (openssh, dropbear, redis, rdp, mssql, vnc, mongodb, rabbitmq, activemq, proftpd, exim, rsyncd, jdwp) for both sides' tests. The version 9 results are frozen under `fixtures/results/v9/`.
- **Contract 9: the `version_rows` kind, so cvENGINE can read the exact Apache, OpenSSL and PHP releases a status page states without the page leaving the Sentinel.** Apache's `/server-status?auto` prints `ServerVersion: Apache/2.4.57 (Debian) OpenSSL/3.0.11` whatever `ServerTokens` says, and a phpinfo page a scan already found prints the PHP, OpenSSL, cURL, libxml2, PCRE, SQLite and Apache releases, next to the environment, cookies and credentials. `version_rows` (`probes.version_read`, `kind_since` 9, so a Sentinel of contract 8 or older is never offered it; the version 8 results are frozen under `fixtures/results/v8/`) takes a `version_read` target whose requests may also use the read `rows`: only the rows the request names come back (a `Name: value` line of a plain-text page, or the first two cells of an HTML table row), each a value of at most 120 version-like characters with a dotted number or a bare build number in it, so even a named row that holds a password stays here. `version_read` and `version_digest` are unchanged and refuse a rows read.
- **More versions read from the pages the version probes already fetch.** The `error-page` probe reads Apache's whole footer banner (`Apache/2.4.6 (CentOS) OpenSSL/1.0.2k-fips PHP/7.4.33 Server at ...`: the web server and the OpenSSL, PHP and Python releases it lists, where it used to miss a footer with modules) and JBoss Web's (`<h3>JBoss Web/7.0.13.Final</h3>`, JBoss AS 4 to 7 and EAP 5 and 6). The Server header names the releases of Werkzeug, Tornado, CherryPy, Apache CouchDB, Squid, RomPager, thttpd, mini_httpd, Boa, WEBrick, Resin, Tengine and Cherokee, each from the project's own version constant. The generator tag reads MkDocs and its Material theme (`mkdocs-1.5.3, mkdocs-material-9.4.8`), and keeps Ghost, Joomla and TYPO3 without a version when their tag states only a line (Ghost prints major.minor), so a line is never matched as a release. `js_libraries` reads Vue 3.4 and later from the banner every Vue package build starts with (`* @vue/runtime-dom v3.4.21` then `* (c) 2018-present Yuxi (Evan) You`).
- **Contract 8: the `version_digest` kind, so cvENGINE can pin the build of an internet-facing VPN or edge appliance from a static file without the file leaving the Sentinel.** Most CISA KEV entries are in such appliances, and their build shows in what their static files are, not in what they say: NetScaler's `rdx_en.json.gz` carries the firmware's build time in its own gzip header. `version_digest` (`probes.version_read`, `kind_since` 8, so a Sentinel of contract 7 or older is never offered it; the version 7 results are frozen under `fixtures/results/v7/`) takes a `version_read` target whose requests may also use the read `digest`: the answer carries the SHA-256 of the body (only when the whole body was read, at most 300 KB) and its first 16 bytes as they came over the wire, in hex, before any content decoding (a file's magic number and header), never the body. An answer another path served after a redirect is marked `redirected` and carries no digest, so a catch-all login page is never handed back as the asset. `version_read` itself is unchanged and refuses a digest read, so a contract 7 Sentinel keeps running it. `probes.http.probe_url` now also returns `sha256` and `wire_head` (`transport.read_body` takes `wire`).
- **Contract 7: the `version_read` kind, so cvENGINE can read a product's version from where the product states it, with no Sentinel release per product.** cvENGINE missed CVEs in components it never put a version on, although Grafana, Jira, Kibana, Vault, Docker, Kubernetes and a Prometheus exporter all say their exact version to anyone who asks. The catalogue of where each product says it (and how to read it) now lives on the server; the new kind `version_read` (`probes.version_read`, contract version 7, `kind_since` 7, so an older Sentinel is never offered it; the version 6 results are frozen under `fixtures/results/v6/`) only runs the GETs a task lists, up to 4 per web base and 100 bases per task, under the task's scope policy, and hands back only the part of each answer the request names: the dotted fields of a JSON object (each a clipped scalar, or a container's type and size), an excerpt from a literal, the `*_info` samples of a metrics page with only their version-like labels, or nothing of the body. A body never leaves the Sentinel whole: an actuator `env`, Consul's `DebugConfig` or Nomad's agent configuration carry secrets, and only the version fields come back. There is no method field (GET only), no cookie or authorization header is ever sent or returned, a path is checked to stay on the base, and every string is stripped of control characters and clipped.
- **Contract 6: the `java_runtime` kind, and the Java runtime of a host read from what it already says.** A runtime CVE (one in the JDK itself) matched nothing because cvENGINE almost never knew a host's Java version from outside. `cvengine_scanner.java` reads it, without asking for anything that is not already public: the JDWP `VirtualMachine.Version` reply (the 14-byte handshake and that one command, exactly what nmap's jdwp-version sends; no other JDWP command exists in the code), Spring Boot's actuator (`env/java.version`, `info`, `metrics/jvm.info`, Boot 1's `env/java.version`), Jolokia's Runtime MXBean, the status pages of Solr, GeoServer, Druid and Elasticsearch or OpenSearch, `X-Powered-By` (GlassFish, Payara: `Java/Azul Systems, Inc./17`) and JVM banners in a page. Versions are normalised to one spelling (`1.8.0_392` is `8u392`, `21.0.2+13-LTS` is `21.0.2`, a bare `17` is the line only) and vendors to one list (Oracle, Eclipse Temurin, Azul, Amazon Corretto, Red Hat, Microsoft, IBM Semeru, BellSoft Liberica, SAP Machine, Debian, Ubuntu, OpenJDK). Every reader reads a fixed set of fields (an actuator `env` or Druid's properties carry secrets: only the `java.*` version and vendor keys are looked at) and returns nothing for any other shape. The new kind `java_runtime` (`probes.java_runtime`, contract version 6, `kind_since` 6, so an older Sentinel is never offered it; the version 5 results are frozen under `fixtures/results/v5/`) runs the fixed GETs for the checks cvENGINE chose per host and the JDWP exchange on the endpoints it names, under the task's scope policy and this Sentinel's floor. The version probes' `headers-root` and `error-page` read the same headers and banners from the pages they already fetch (an observation of the product `Java runtime`, never a technology). The fingerprint pass also scans the common Java debug ports (5005 to 5010, 8787, 9009), where nmap's own jdwp-version (a version script -sV runs by itself at intensity 7) names the service.

### Fixed
- **A long bbot screenshot name keeps its extension.** The client cut a screenshot's file name at the contract's 120 characters, which could drop the `.png` or `.jpg` of a gowitness name made from a long URL, and cvENGINE drops a screenshot whose extension does not match its content type. The stem is cut now, never the extension, and a name whose extension is not the picture's type (or that has none) gets the type's own (`client.bbot._screenshot_name`).
- **`nmap_udp`: the contract says 512 KiB, as the server does, and the client stops a larger report.** The result contract still allowed a 4 MiB `xml` for `nmap_udp`, but cvENGINE refuses more than 512 KiB (`agentapi.sentinel_broker.MAX_NMAP_UDP_XML`; `nmap_full` and `nmap_verify` keep 4 MiB). The contract's `maxLength` is 524288 now and `run_nmap_udp` stops nmap at that size (`MAX_NMAP_UDP_REPORT`, a `ToolOutputError` as for the other report caps) instead of sending a result the server throws away. 18 UDP ports of one address are a few KiB. A tighter bound is accepted by every server, so the contract version is unchanged.
- **OpenVAS: the openvas-scanner image pin points at an image that exists.** Greenbone replaced the image behind `stable` and the pinned digest `c9dd880d...` is gone from its registry (`scripts/greenbone-digests.sh` said MISSING, and the OpenVAS integration run has been red on `main` since 2026-11-17), so `docker compose --profile openvas up` could not pull it. Both openvas-scanner services now pin `sha256:a580aab7...`, the current `stable`; every other Greenbone pin is unchanged and current.
- **The credential rule also catches `pw=`, multipart form fields, a body written inside a string (`\"password\":\"x\"`) and a URL-encoded field name; no pattern can take long on hostile text.** A field named `pw` (as a whole name), a multipart `name="password"` part with a fixed value, escaped-quote JSON or GraphQL text and `p%61ssword=x` were approved by both rules and sent a vendor default password (12 of the 14,225 community templates are newly left out while the switch is off; `RULE_REV` 5, so every Sentinel makes its list again). A pattern that could rescan an unclosed `{{` from every position took 45 seconds on 190,000 characters; the patterns are linear now and a test times each shape.
- **A Sentinel on Automatic that has no target waits instead of reporting "update failed" every hour.** `scripts/update.sh` records `waiting: the server named no target` (to cvENGINE once a day) and exits 0; so does a target older than what runs (a server that pins an older build than the Sentinel).
- **Test fix: the heartbeat interval test waits for its two beats with a deadline** (the Image workflow was red on 97d52f46 on a busy runner).
- **The Sentinel container keeps two capabilities, not the Docker defaults plus `NET_ADMIN` (SN-8).** `cap_drop: [ALL]`, then `NET_RAW` (nmap SYN scan, OS detection and UDP sweep, naabu) and `SYS_CHROOT` (Chromium's sandbox). `NET_ADMIN` is gone, which matters most with host networking, where it reached the host's routes, firewall and interfaces; the file capability on nmap and naabu is now `cap_net_raw` alone. A new CI run starts the built image through the compose service and runs nmap -sS, -O and -sU, naabu, nuclei, WPScan, wafw00f, testssl.sh, Kingfisher, sshamble and bbot against its own loopback. `no-new-privileges` is not set (it disables file capabilities, so raw sockets then depend on the engine's version) and the root filesystem stays writable (bbot's discovery needs `~/.bbot/tools`); README "What docker-compose.yml sets" says why.
- **A Sentinel on Automatic updates moves only to the commit cvENGINE named (SN-3).** `scripts/update.sh` (and `scripts/pull-on-exit.sh`) used to build whatever was at the head of `origin/main`. It now moves to the heartbeat's `target` and refuses, reports a failed update and leaves the running Sentinel as it is when cvENGINE named none, the commit is not in the fetched history or not reachable from `main`, or it is not a descendant of the running commit; `HEAD` must equal the target before anything is built. A person can still run `scripts/update.sh --now` (head of `main`, with a message saying what that trusts), `--to COMMIT`, and `--allow-non-descendant` for a rollback. Commits are not signature-checked in 1.4.0; README "What Automatic trusts" says what is trusted and how to stay on Manual.
- **The credential rule also reads request bodies, and sees a fixed value behind a placeholder.** A form, JSON or XML field named like a password (`password`, `passwd`, `pwd`, `passphrase`, `j_password`, `userpass`...; not `bypass`) with a fixed value in a `body`, a query string or a raw request body is a credential, as is a header or field whose placeholder names a variable that holds a fixed value (also through another variable) or a payload list (`Basic {{base64(auth)}}` with `auth: admin:admin`). A value that is only a placeholder (what a signed-in run supplies) is not. On nuclei-templates v10.5.2 the reviewer's scripts found 112 body-password templates not refused (36 with a common default password): now 3 remain, none with one; 6 `authenticated` templates with a fixed password variable and 4 helper headers: now none. The byte prefilter also parses any file with a YAML escape (`\x2f`, `\u0040`, `\/`, a trailing backslash), so an escaped user-info URL is no longer skipped. 837 of the 14,248 templates are left out of a run that may not send credentials (15.6 s before; 18.3 s and 52 MB peak in the child process now). The Sentinel says `credential_filter` in `info.features`, which the server needs before it hands such a Sentinel web checks while credential checks are off.
- **The read-only rule refuses a template that sends a credential of its own.** A header that authenticates (`Authorization`, `Cookie`, `X-Api-Key`, a token...) with a value the template fixes (`Basic ...`, `Bearer ...`, a session id, `{{base64('admin:admin')}}`), in a block's `headers` or in a raw request, and a URL with a user name in it, make `checks.readonly_problem` refuse the template (`checks.credential_problem`, mirrored by the server and tested on the shared corpus). A header made only of placeholders (what a signed-in run or an extractor supplies) is not refused. Four corpus cases that said such a template was read-only now say it is not. A nuclei web run that does not carry `allow_credential_checks` also leaves such templates out of the installed set (the image's baked templates, or a server bundle) with `-exclude-templates`, from a list made once per templates release (15.6 seconds and 47 MB peak resident memory for the 14,248 templates of v10.5.2, made at start in a child process with a 512 MB address-space limit and a 300 second limit, and kept on disk; made again when the release, the files or the rule change) and reported in `cuts` as two counts, `templates_with_credentials` (377 in v10.5.2) and `templates_unreadable` (none). Only a file whose bytes could hold a credential (`checks.might_send_credential`, built from the rule's own tables) is parsed, and one at a time; the result equals a full parse of every file. A file that kills the child is counted unreadable and the scan goes on after it. Installed templates are judged at their real size (up to 32 MB; the 10 MB WordPress plugin detection feed stays in): the 200,000 byte limit stays for text handed to a rule. If the list cannot be made the web pass does not run, and its targets stay due; the unfiltered set is never run in its place. A template that cannot be read or parsed is left out too, and counted apart.
- **nuclei: the web pass sends no credentials unless the task says a person turned that on.** `default-login` and `bruteforce` templates (they POST vendor default logins to login forms) are in the exclusion of every web and local nuclei run, and a targeted tag filter never names them; the task field `allow_credential_checks` (optional, absent or false means off, an older server never sends it) lifts it for the web pass only. The service-port runs never send credentials, whatever the task says.
- **nuclei: a service with no allowlisted check is reported as no check, not as unreachable.** A postgres or other port of a class no template speaks to was named unreachable and not checked, so the server failed it and asked again every day. It is now named only in `not_checked` ("no check exists for this service"); a service-port list that did not load is still unreachable, and says so.
- **nuclei: ten read-only service templates are back on the allowlist.** `mongodb-detect`, `mongodb-info-enum`, `ldap-metadata` (LDAP's first check), `rdp-detection`, `samba-detect`, `rtsp-detect`, `nats-server-enum`, `gost-ssh-detect`, `gost-socks5-detect` and `apache-rocketmq-broker-unauth` (v10.5.2). Each was read: none sends a credential or changes anything on the target (the reasons are in `nuclei_service_review.json`). MongoBleed (CVE-2025-14847), SMBGhost and the empty-password logins stay out.
- **db_probe: a port that did not answer is unknown, not "authentication required".** A refused connection, a timeout or a reset gave `open: false`, which the server counts as checked and not exposed. It is now `null` (unknown, the server keeps it due); `false` only when the server answered and refused.
- **identity_check stops starting questions after 240 seconds.** Up to 200 DNS questions and 50 certificates ran one after another, so a slow resolver could keep the Sentinel working past the 300 seconds the server waits, and the result was thrown away. The rest are reported unknown, not run, and asked again.
- **Contract 5: the nmap fingerprint pass keeps what nmap learned, and nothing is cut silently (TL-1, TL-9, TL-13, SN-4, SN-6, SN-9).** Strictly additive: every new field is optional, so a contract 4 server keeps working and a contract 5 server takes a contract 4 Sentinel (`min_supported_contract_version` stays 1; the version 4 results are frozen under `fixtures/results/v4/`). `parse_nmap_xml` kept only the number, protocol, name, product and version of a port: it now keeps the extra info, CPEs, how the service was found, whether it is wrapped in TLS (`tunnel`), the banner, the certificate summary (subject, issuer, names, validity, fingerprints) and the reviewed NSE scripts' output (4000 characters a script, 16000 a port), and per host the OS accuracy and runners-up, the host scripts, the closed TCP port OS detection used (`closed_tcp`, which the path check needs), the ports the run probed (`scanned_ranges`) and the states of the ports nmap did not list (`extraports`). Port 443 is no longer plain `http`, and an FTP server that offers TLS shows its certificate. Every text came from a scanned host: control characters are removed and each field is clipped. A new `cuts` list on the nmap, nuclei, bbot_discovery and secrets_scan results says what was cut, in one shape (`what`, `kind` of `items`, `chars` or `time`, `limit`, `dropped`, `target`): bbot events, http responses and screenshots past their run caps and its time limit, nuclei findings over the cap and clipped evidence, nmap ports over 500 a host and a host nmap gave up on, secrets findings over 500 and clipped lists. A bbot `FINDING` carries its `port` (optional, in a partial batch). The registration and every heartbeat carry `info.tool_versions`. The server side (storing, showing) is a pull request of its own.
- **Smaller bounds and fixes from the 1.4.0 review.** bbot keeps a name's IPv6 resolutions (a host with only AAAA answers had no address). A template test's hit on another port of the host is not a hit for the `host:port` asked. A check's `network` `inputs` `read` must be 1 to 65536, and `ssl` and `dns` blocks count toward the six-request limit of an AI-written check (`check_allowlist.py`, `checks.py` and the shared corpus; the server copies the corpus and allowlist when it next moves its pin). The client reads at most 8 MiB of any server answer.

The task now carries an optional `services` map (what speaks on each `host:port`: `web`, `unknown`, or a protocol class such as `ssh`, `smtp`, `imap`, `tls`) and a `budget`. The web targets run first, together, without the raw tcp and javascript templates and with a per-host rate (25 requests a second a host, `-per-host-rate-limit`). An unknown port whose banner probe is read is charged to that port's time budget, and a host name is resolved once, for the scope judgment, and the probe connects to the address that was judged. Measured on nuclei 3.11.1 with sshd on 2222 and a counting listener on 22 of the same host: the ssh javascript templates (`Port: "22"` in their arguments) connect to the target's own port, 2222, and none opened a connection to 22. A port that is only partly checked (out of time part way, some runs failed, the template listing failed) is also reported as unreachable so the server keeps it due. An unknown port that answers with an SSH banner on connect (one short connection, nothing sent; not through an egress proxy) is treated as ssh. ### Added
- A Sentinel that is not the built-in scanner now reports `info.features: ["bbot_keys"]` in its heartbeat: it reads a bbot discovery task's API keys through the
  single-use secret read (`POST sentinel/tasks/<id>/secret`), keeps them only in a 0600 file inside a fresh 0700 directory for the run, and masks them. A cvENGINE
  server sends the project's discovery API keys only to a Sentinel that says so (and that its owner has not opted out); an older Sentinel never says it and never gets
  them. Optional field, no contract change, no new task kind, task payload unchanged. Every key is now also masked in each batch posted and in the final result and
  any error text (not only in bbot's error stream), and a key directory a crashed run left in the temp directory is removed at the next start.
- A Sentinel watchdog (`client/watchdog.py`, docs/WATCHDOG.md): a thread apart from the task threads, ticking every 10 seconds, on by default
  (`CVENGINE_SENTINEL_WATCHDOG=0` switches it off). W1 stops a task's whole process group at a per-kind hard deadline (the tool's own budget plus a grace; the
  owner can raise it, never lower it) and reports `error` "timed out after N minutes"; W2 stops a group that used no CPU and moved no bytes for N minutes (a
  hung tool); a stopped nuclei run that had printed findings reports them as `done`, one with none is an `error`. W3 breaks the memory-budget deadlock: waiters that
  waited 3 minutes behind long runs may start inside an overcommit of at most 25 percent of the budget and only within the real free memory measured from /proc and
  the cgroup (a floor of the larger of 300 MB and 15 percent of the limit); nothing is killed for it. W4 kills tool process groups that outlived their task and reaps
  their zombies. W5 replaces a stuck heartbeat thread and ends the process (exit code 3) for a poll loop stuck for 5 minutes, for every Sentinel; the image health
  check also fails on a stale watchdog, heartbeat or poll loop. W6 stops taking work under 300 MB of free disk and removes only its own temp and cache files.
  W7 the heartbeat's optional `info.watchdog` (last tick, actions, kills, overcommit, reasons). W8 per-rule variables, one log line per action, and a kind
  stopped 3 times in an hour is not asked for for 30 minutes. No contract change, no new task kind.
- **AI-written checks run on your own Sentinels (contract version 4).** With no built-in scanner, cvENGINE now sends its AI-written and approved
  nuclei checks (`nuclei_validate`) and its scan path survey (`path_probe`) to the project's own Sentinels. A Sentinel that is not the built-in scanner
  runs a check only when all of these hold: the task names the sha256 of the template (`template_sha256`), the file it wrote and read back hashes to it,
  its server names the same hash and mode for that task when asked separately (`GET sentinel/tasks/<id>/check`), the template passes the server's
  read-only rules (`cvengine_scanner.checks`, one shared test corpus) and it reaches only the task's own target and port (no literal port, no `port`
  key). A result line for a host the task did not name is never a hit, and the result echoes the hash it ran. The image gains PyYAML 6.0.3.
  Second security pass: the whole template is held to an allowlist (`cvengine_scanner.check_allowlist`): one YAML document that PyYAML and
  nuclei's yaml.v3 read alike (no duplicate keys, second document, anchors, merge keys, tags, YAML 1.1 words, U+2028), known keys only, and every
  `{{...}}` expression, `dsl` string and variable may call only side-effect-free string, encoding, hash and compare helpers (no `resolve`, `jarm`,
  `public_ip`, `wait_for`, `print_debug`, clock or random helpers); a raw request is exactly one GET, HEAD or OPTIONS request with no body or `@`
  annotation, and no request sets `Host` (outside raw), `Authorization`, `Cookie`, a forwarding header or a credential-looking value. The server's
  check answer names the task's sorted targets too, compared with the task's (hashes with `hmac.compare_digest`). nuclei is pointed with `-r` at a
  resolver of the Sentinel's own that answers each target name only with the addresses scope judged and nothing else (a name whose answer changes after
  it was judged still reaches only the judged address; an install proxy resolves the name itself, outside this resolver, and a name with non-ASCII
  letters is pinned in its Unicode form while nuclei asks in punycode, so it gets no answer), and
  runs with a minimal environment (no Sentinel secret), a 2 GiB data limit, its time limit and a 16 MiB cap on the output read. The hash protects
  against a check changed in transit, edited after dispatch or changed on disk before the run; not against a compromised server, against which the
  Sentinel's own allowlist and target limit are the defence.
  Third security pass: a string literal in an expression may not contain a quote character of either kind (nuclei before 3.9.0 ended a string at either
  kind, which hid a `resolve()` call from the allowlist), and a Sentinel refuses to run an AI-written check on a nuclei older than 3.9.0 or with no
  readable version; the gate refuses with a reason instead of raising on a deeply nested document or a value of an unexpected type (nesting is capped at
  20); names are matched whole (no trailing newline); control characters and U+00A7 are refused in decoded strings too; a plain decimal such as
  `cvss-score: 9.8`, CRLF line ends, upper-case metadata keys and a list of authors are accepted (both YAML readers read them the same way).
